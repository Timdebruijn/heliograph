## 0 · Build-system reality (read this first)

The brief is written in ESP-IDF idiom (`idf.py size-components`, per-variant
`sdkconfig.defaults`, Kconfig). This project is **Arduino core 3.3.9 on IDF 5.5.4 via
pioarduino, with prebuilt IDF libraries** (`platformio.ini:129`, verified banner
`platformio.ini:126-128`). Consequences that shape everything below:

- The IDF `sdkconfig` is **fixed per memory-type flavor** of the prebuilt core
  (`~/.platformio/packages/framework-arduinoespressif32-libs/esp32s3/<flavor>/include/sdkconfig.h`).
  The project chooses a flavor per board (`board_build.arduino.memory_type`), nothing finer.
- Anything the brief frames as "tune this sdkconfig value" — cache size, UART ISR
  placement, lwIP buffer sizes, FreeRTOS tick — is **not expressible** in this build
  system short of building the Arduino core from source (a real option, but it is
  variant machinery and counts as such in any proposal).
- `idf.py size-components` does not exist here; static sizes come from `pio run`
  section totals and `.pio/build/<env>/firmware.map`.

### Discrepancies against the task brief

1. **RS485 direction, A/B.** The brief says A has "hardware-automatic direction
   control". The code *drives DE on GPIO21* — but via
   `uart_.setMode(UART_MODE_RS485_HALF_DUPLEX)` after handing the pin to the UART
   (`src/transport/rs485_transport.cpp:58-63`). That is the S3 UART peripheral
   toggling DE in silicon, not software bit-banging. C (`kRs485De=-1`) relies on the
   board's own auto-direction circuit, hardware-verified 2026-07-23. **Net result:
   no software-timed DE anywhere; the timing-critical divergence the brief warns
   about does not exist in this codebase.** What remains variant-specific is only
   *which* hardware does it.
2. **GPIO21 is double-booked across variants by design:** RS485-DE on A/B, buzzer on
   C. Correctly encoded per board header; worth knowing when reading schematics.
3. **C flash is 8 MB, not 16** — confirmed (`platformio.ini:246-248`), with its own
   partition table. The brief asked to verify rather than assume: verified.
4. **CAN:** pins are declared on A's header and *nothing else exists* — zero TWAI,
   MCP2515 or DS3231 code anywhere (`grep -rniE "twai|mcp2515|ds3231"` hits only the
   two board headers). See §7.

## 5 · Timing-critical paths

1. **RS485 transaction.** Bus owned by one task; drivers run a transaction deadline
   (host-tested, `test/test_eversolar/driver.cpp` covers deadline under noise,
   resync, echo-skip). DE is peripheral- or board-hardware-driven on every variant
   (§1.1) — no software inter-frame timing to break. At 9600 baud a byte lasts
   ~1.04 ms; the 128-byte UART hardware FIFO therefore absorbs ~130 ms of stall
   before data loss.
2. **Flash writes vs the flash-resident UART ISR.** NVS commits (config saves) and
   OTA writes disable cache; with `CONFIG_UART_ISR_IN_IRAM` unset the UART ISR
   cannot run in those windows. The FIFO math above says a stall shorter than
   ~130 ms is invisible at 9600 baud. Typical NVS commit is well under that;
   OTA writes happen in ~4 KB chunks with cache-disabled windows of single-digit
   ms each. UNVERIFIED at the edges: worst-case erase of a full NVS page during a
   poll. Phase-3: timestamp a config-save during an active poll on A, watch for a
   timeout tick in diagnostics. C identical mechanism (same flavor setting).
3. **Watchdog.** 120 s budget, per-probe feeds during discovery (§2). The stated
   cost (slow idle-starvation detection on core 0) is documented in-code.
4. **OTA.** Runs on `async_tcp` (prio 10); `rs485` keeps polling through it. The
   0.24.1 OTA on A today showed exactly one boot-window poll failure, none during
   download. Rollback: dual slots + healthy-boot confirmation gated on network + a
   successful poll (`loop()`, `src/main.cpp` — `ota::shouldConfirmHealthyBoot`).
5. **Time.** The core never uses wall-clock: `ClockFn` is *milliseconds since boot*
   (`src/device/clock.h:13`), measurements are stamped `timestampMs` (monotonic,
   `measurement.h:72`), payloads publish ages, not epochs (no `epoch|time(nullptr)`
   hits in payload builders). Wall-clock exists only at the edges: log-line
   prefixes (documented 1970 fallback pre-sync, `log_timestamp.cpp:16`), RTC
   write-back after NTP (A/B), TLS cert validation for the update check. **On C the
   pre-NTP window therefore produces mislabelled log *timestamps* (wrong-looking
   data) but no wrong measurements** — sharper claim than the brief feared, to be
   re-verified in Phase 2 when walking the MQTT/HA payloads in full.

## 6 · Build config summary (fixed by core flavor)

Identical between `qio_opi` (A/B) and `qio_qspi` (C) except SPIRAM mode:

```
CPU 240 MHz · flash QIO @ 80 MHz · FreeRTOS tick 1000 Hz
I-cache 16 KB / 8-way / line 32 B   ← already the minimum; NOT tunable here
D-cache 32 KB / 8-way / line 32 B
SPIRAM_USE_MALLOC=1, ALWAYSINTERNAL=4096, RESERVE_INTERNAL=0   (OCT on A/B, QUAD on C)
UART_ISR_IN_IRAM: not set
lwIP: TCP_SND_BUF 5744, TCP_WND 5760
mbedTLS: hardware AES/SHA/MPI on
Console: UART + USB-Serial-JTAG secondary
```

Notable: **C runs a core compiled with quad-SPIRAM support against a board that has
none** — the boot-time probe fails gracefully (that is the "no more octal bailing
out" fix of 2026-07-23; there is no PSRAM-less S3 flavor to pick). Cost: a probe at
boot, dead SPIRAM code in flash, zero RAM cost. UNVERIFIED: whether the quad probe
logs anything at current log level — worth one boot-log read on C.

The build system **can** express per-variant differences at the board level (env +
`board.h` constants + partition table + memory_type + feature defines) and does so
correctly today. It **cannot** express per-variant IDF config. Any proposal needing
the latter must budget for building the core from source or migrating that
component to ESP-IDF-as-framework — both are Tier-2-sized machinery.

## 10 · Findings

Format per finding: mechanism → evidence → variants → impact / effort / risk /
confidence. "Measure first" means the finding is real but its *size* is unproven;
no change should land before the measurement.

### F1 · `async_tcp` floats across both cores at priority 10, above the poll task

- **Mechanism:** `CONFIG_ASYNC_TCP_RUNNING_CORE -1` (`AsyncTCP.h:37`) lets the
  scheduler place the web/Modbus-TCP service task on core 1, where it preempts
  `rs485` (prio 5) mid-transaction. The UART FIFO prevents data loss; what it can
  add is read-loop latency inside the transaction deadline, i.e. poll jitter under
  dashboard or Modbus-TCP load. Never chosen: no override exists, `git log -S`
  empty.
- **Variants:** all. **Impact:** unknown until measured — possibly zero at 9600
  baud. **Effort of the candidate change** (`-DCONFIG_ASYNC_TCP_RUNNING_CORE=0`):
  one build flag; core 0 then hosts WiFi+lwIP+web, core 1 keeps Arduino+polling.
  **Risk:** low, trivially reversible; the counter-risk is starving web service
  behind WiFi bursts — which the measurement must catch. **Confidence** that the
  mechanism exists: high; that it matters: medium-low.
- **Measure first (A, then C):** `CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS 1` is
  available in the prebuilt core (verified in flavor sdkconfig.h), so
  `vTaskGetRunTimeStats()` works. Temporary debug endpoint or serial dump; compare
  poll-duration distribution (needs F7) with dashboard closed vs open vs open+Modbus
  scrape, floating vs pinned.

### F2 · Dashboard-open is the lead suspect for the 78.7 KB min-free dip

- **Mechanism:** the page's refresh cadence fetches several JSON endpoints while
  SSE runs; each response is built ≤ 8 KB (`kMaxResponseBytes`,
  `rest_payloads.h:20`) into per-connection AsyncTCP buffers backed by lwIP
  socket buffers (`TCP_SND_BUF 5744` each); a browser holds up to ~6 concurrent
  sockets. Stacked transients of tens of KB are plausible; Tim confirms the page
  was open during the dip window.
- **Variants:** all; the number that matters is C's floor (last known low-water
  87 KB on 0.12.0 — stale). **Impact:** no leak (heap returns to ~152 KB); this
  defines the *crash margin* under worst-case concurrency (page + discovery +
  backup download). **Effort/risk:** none — measurement + possibly "accept".
  **Confidence:** high on attribution path, medium on magnitude.
- **Measure first (A now, C when connected):** reboot to reset the boot-anchored
  `minimum_free_heap_bytes`, then staged load: 10 min idle → page open → page +
  capture → page + backup download; record the stepwise min-free after each stage.

### F3 · PSRAM does nothing on A/B — by policy, and that is a choice to make

- **Mechanism:** `SPIRAM_MALLOC_ALWAYSINTERNAL 4096` + a codebase that allocates
  small (log ring static, responses ≤ 8 KB, bodies ≤ 4 KB, ArduinoJson pooled)
  → nothing crosses the threshold. Live: 8 378 140 of 8 388 608 B free.
- **Variants:** A/B have the idle silicon; C defines the behaviour floor.
- **Options:** (a) **accept** — one heap behaviour on all variants, zero
  divergence, zero effort (my recommendation, and it is what your own variant
  rule optimises for); (b) move *named* large consumers (capture frame store,
  a deeper log ring) to explicit PSRAM on A/B — gains headroom A/B only,
  **diverges C**, and the C fallback path must then be host-covered per your
  constraint. **Impact of (b):** more capture/log depth on A/B; nothing on C.
  **Effort (b):** small-medium. **Risk (b):** the exact divergence class your
  brief flags. **Confidence:** high.

### F4 · `RTC_NOINIT_ATTR` is unused — C's only reset-forensics lever lies idle

- **Mechanism:** RTC-domain SRAM survives panic/WDT/soft reset on all three
  variants without any battery or clock. Today the only post-reset evidence is
  `reset_reason` + a coredump partition. A small CRC-guarded breadcrumb struct
  (boot counter, uptime-at-death, last poll state, reset-reason ring) would give
  C — which cannot timestamp anything pre-NTP — *ordered* failure evidence, and
  A/B better evidence than wall-clock-less coredumps alone.
- **Evidence:** zero `RTC_NOINIT|RTC_DATA_ATTR` hits in `src/`; coredump
  partitions in both CSVs.
- **Variants:** all; biggest value C. **Impact:** diagnosability, not
  performance. **Effort:** small (struct + CRC + `/diagnostics` exposure; logic
  host-tested via injected storage, target attribute is one line). **Risk:** low.
  **Confidence:** high.

### F5 · espMqttClient outbox can grow while a broker is slow-but-connected

- **Mechanism:** the outbox is an unbounded heap linked list (`Outbox.h:29`,
  mempool off by default `Config.h`); our layer gates on `connected()` only
  (`mqtt_output.cpp:246,366`). A half-open or zero-window broker keeps
  `connected()` true while every poll cycle enqueues; growth ends only when the
  client's own timeout tears the socket down. Worst case sits on top of F2's
  transients, against C's floor.
- **Variants:** all (C floor). **Impact:** robustness margin during broker
  misbehaviour, not steady state. **Effort of remedy:** small (skip enqueue above
  an outbox/heap threshold) — but design after measurement. **Risk:** low.
  **Confidence:** medium — the growth *rate* (~1-2 KB per device per 10 s cycle)
  and the teardown timing are the unknowns.
- **Measure first (A, then C):** hostile-broker test — accept TCP, stop ACKing
  (iptables/toxiproxy) — watch free-heap slope and recovery.

### F6 · Nagle on Modbus TCP / SSE / web: non-issue, verified

`setNoDelay(true)` per accepted client and server-wide in eModbus
(`ModbusServerTCPasync.cpp:21,209`), on SSE clients (`AsyncEventSource.cpp:185`)
and the web server (`WebServer.cpp:113`). Nothing to do.

### F7 · There is no poll-duration metric — measurement infrastructure gap

- **Mechanism:** diagnostics counts successes/failures/backoff but records no
  transaction latency; every latency statement (including F1/F2 above) currently
  rests on "no timeouts observed" rather than a distribution.
- **Variants:** all. **Impact:** unblocks F1, F2, F5 measurements without JTAG.
  **Effort:** small (min/max/EWMA per poll into `/diagnostics`; host-tested).
  **Risk:** negligible. **Confidence:** high. *This is the one code change worth
  doing before any other, because three measurements depend on it.*

### F8 · Cache, IRAM, peripheral offload: non-issues, with evidence

I-cache already at the 16 KB minimum and not tunable (prebuilt core, §0/§6). No
own ISRs to place in IRAM. DE is silicon/board-hardware on every variant (§1).
ESP32-S3 ROM has no Modbus-CRC16; the software table is correct engineering.
Hardware AES/SHA already on (§6). UART@9600: the 128-byte FIFO absorbs ~130 ms of
flash-stall, far above NVS/OTA cache-disabled windows. One UNVERIFIED edge —
worst-case NVS page GC during an active poll — parked as a low-priority
measurement (config-save storm during polling, watch for one timeout tick).

### F9 · Wall-clock on C: contained, one cosmetic choice left

The core is monotonic ms-since-boot end to end (`clock.h:13`,
`measurement.h:72`); payload builders emit no epochs (grep-verified). What remains:
log-line prefixes print 1970 dates before NTP (documented fallback,
`log_timestamp.cpp:16`) and reset events carry no wall time — which F4 addresses
without needing a clock at all. "Wrong data" exposure = log ordering across a
reboot, nothing else found.

### F10 · Stack sizing: roughly right, C unconfirmed

Live A: `rs485` 3 536 B free of 8 192, `loop` 3 752 of 8 192 — neither tight nor
wasteful enough to touch under the readability-over-bytes rule. espMqttClient logs
its own HWM at teardown (`MqttClient.cpp:322`). C numbers pending its measurement
round.

## 12 · Out of scope / rejected

- CAN/TWAI/MCP2515 work of any kind — no code exists, no roadmap (Tim, Q3).
- DS3231 support — no hardware in the fleet, C runs clockless by design.
- Replacing the data-file driver model or output adapters — constraint, and no
  evidence they cost anything measurable at runtime.
- Cache retuning, IRAM placement, UART DMA, PCNT/RMT offload — §F8, mechanisms
  absent or already optimal.
- Core-from-source / ESP-IDF migration to unlock sdkconfig — no current finding
  justifies that machinery.
- Reclaiming stack headroom — readability rule outranks ~9 KB total.
